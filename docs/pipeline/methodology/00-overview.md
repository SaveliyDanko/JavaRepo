# AI Pipeline — Обзор

Карта пайплайна по работе с LLM-агентами: от идеи нового репозитория до
проверенного кода. Каждый этап — отдельная роль (промт), которую агент
читает и выполняет. Это точка входа; детали — в файлах ролей.

## Базовые принципы (общие для всех ролей)
- **Артефакты — в файлах, не в чате.** В чат идут только вопросы, статус,
  ссылки на файлы и запрос подтверждения.
- **Минимализм.** Ценность на строку, а не объём. Детализация — по запросу.
- **Резюмируемость.** Любой этап можно прервать и продолжить по статусам в
  файлах — другой агент подхватывает без памяти предыдущего.
- **Подтверждение между этапами.** При неоднозначности — стоп и вопрос.

## Режим и общие правила (сквозной слой)
Поведение всех ролей параметризуется двумя файлами (копируются в корень
репозитория проекта):
- `pipeline.config.md` — «пульт»: режим (`interactive` / `mixed` /
  `autonomous`), политика гейтов, лимиты, каналы вмешательства.
- `common-rules.md` — «устав»: как роли исполняют гейты, когда эскалируют,
  как человек вмешивается.

Каждая роль начинает с «Шага 0»: прочитать оба файла. Гейты (handshake'и
ниже) проходят по политике из конфига: `manual` ждёт человека, `auto`
проходит с записью в `docs/decisions.md`, `auto-with-guard` — только если
проверки зелёные, иначе эскалация в `docs/escalations.md`. Гейты двух типов:
**внутренние гейты роли (GR)** проходит сама роль; **гейты перехода фаз (GT)**
применяет Дирижёр при запуске следующей фазы.

## Оркестрация (Дирижёр)
Над ролями 01–06 стоит `orchestrator.md` — он читает статус-файлы,
определяет текущую фазу проекта, запускает нужную роль и проходит межролевые
гейты по политике из конфига. Своё состояние ведёт в `docs/pipeline-state.md`.
В автономном/мультиагентном режиме он диспетчер; в интерактивном помогает
ответить «где мы и что дальше». Без него мультиагент работает по одной роли за
раз (ручной запуск).

## Роли и поток

| # | Роль | Файл | Вход | Выход |
|---|------|------|------|-------|
| 01 | Проектирование | `01-design.md` | замысел | `docs/design/01..03` |
| 02 | Архитектор (детализация) | `02-architect.md` | `03-implementation-plan.md` | `docs/stages/*` + флаг готовности |
| 03 | Воркер (реализация) | `03-worker.md` | `docs/stages/*` | код + `docs/implementation/progress.md` |
| 04 | Reviewer (ревью) | `04-reviewer.md` | код + план stage | `docs/review/*` + вердикт |
| 05 | Интеграция/приёмка | `05-acceptance.md` | весь проект + требования (01) | `docs/acceptance/*` + вердикт |
| 06 | Изменения (CR) | `06-change-request.md` | запрос на изменение | переоткрытые stages + `docs/change-requests/*` |

```
01 Проектирование ─→ docs/design/01..03 (укрупнённый план)
        │
02 Архитектор ─────→ docs/stages/summary-stages.md + stages/NN-*.md ─→ флаг «готово»
        │
03 Воркер ─────────→ код + docs/implementation/progress.md
        │                       ⇅  петля ревью
04 Reviewer ───────→ docs/review/NN-*.md ─→ approved
        │  (все stages approved)
05 Приёмка ────────→ docs/acceptance/acceptance-report.md ─→ accepted
```

## Поток изменений (change request)
Новое/изменённое требование (смена замысла, а не дефект) оформляется как CR в
`docs/change-requests/CR-NN-*.md`. `06-change-request.md` делает
анализ влияния, определяет минимальный радиус и переоткрывает ТОЛЬКО затронутые
stages (дельту требований/архитектуры правит сам, по карточке CR). Незатронутые
stages остаются `approved`. Дальше работает обычный поток: detail → impl ⇄
review → повторная приёмка. Дефекты против существующего плана сюда не
относятся — это петли 04/05.

## Структура артефактов
```
docs/
  design/
    01-requirements.md          ← 01: резюме требований
    02-architecture.md          ← 01: архитектура (минимализм)
    03-implementation-plan.md   ← 01: УКРУПНЁННЫЙ план
  stages/
    summary-stages.md           ← 02: индекс stages + флаг «Готовность к разработке»
    NN-<slug>.md                ← 02: детальные планы stage (read-only ниже по потоку)
  implementation/
    progress.md                 ← 03: журнал реализации и точка хэндофа
  review/
    NN-<slug>.md                ← 04: замечания (пишет только reviewer)
  acceptance/
    acceptance-report.md        ← 05: приёмка проекта (вердикт)
  change-requests/
    CR-NN-<slug>.md             ← 06: запросы на изменение (карточки)
  pipeline-state.md             ← Дирижёр: глобальная фаза + тик-лог
  decisions.md                  ← все роли: что агент решил сам (аудит)
  escalations.md                ← все роли: что требует человека
  inbox.md                      ← человек: директивы агентам
```

## Handshake между этапами (две развилки)
1. **Архитектор → Воркер.** В `summary-stages.md` флаг
   **«Готовность к разработке»** = `да`, когда все stages детализированы.
   Воркер не стартует, пока флаг ≠ `да`.
2. **Воркер ⇄ Reviewer.** Через статус stage в `progress.md`:
   `ready-for-review` (воркер) → `approved` / `changes-requested` (reviewer).

## Статусы и кто их выставляет

**Детализация stage** (`summary-stages.md`, ведёт архитектор):
`todo → in-progress → done`. Сверяется с фактом наличия файла `stages/NN-*.md`.

**Реализация stage** (`progress.md`):
```
todo → in-progress → ready-for-review → in-review → approved   ← терминальное «готово»
                            ↑                  │
                            └── changes-requested ┘
```
| Переход | Кто |
|---|---|
| `todo → in-progress → ready-for-review` | воркер |
| `ready-for-review → in-review → approved / changes-requested` | reviewer |
| `changes-requested → ready-for-review` | воркер |

**Шаг внутри stage** (`progress.md`, ведёт воркер):
`todo → in-progress → done`; плюс `blocked`.

**Замечание** (`docs/review/NN-*.md`, ведёт reviewer):
`open → verified`. ID `NN-k` стабильны между раундами для ссылок из журнала.

> Важно: статус ДЕТАЛИЗАЦИИ (у архитектора) и статус РЕАЛИЗАЦИИ (у воркера) —
> это разные вещи про один и тот же stage, в разных файлах. Не путать.

## Границы ответственности
- План (`docs/stages/*`) — read-only для воркера и reviewer. Дефект плана →
  сигнал назад к архитектору, а не правка на месте.
- Файл ревью (`docs/review/*`) пишет только reviewer.
- Reviewer read-only по коду; код правит только воркер.

## Как использовать
В нужном репозитории дай агенту прочитать файл соответствующей роли и
следовать ему. Удобно оформить роли как slash-команды (`/design`,
`/architect`, `/work`, `/review`); этот vault — источник правды, команды —
рабочие копии.
