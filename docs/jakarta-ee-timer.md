# Jakarta EE Timer Service

Краткая теоретическая сводка. Код — в `src/main/java/com/savadanko/javarepo/eetimer/`.

> ⚠️ Таймеры исполняет **EE-контейнер** (GlassFish/Payara/WildFly), а не Spring
> и не `java.util.concurrent`. В этой ветке показан только **API** — код
> компилируется против `jakarta.ejb`, но реально срабатывает лишь внутри
> контейнера. Тесты проверяют логику бина напрямую, без контейнера.

## Что это и зачем

**EJB Timer Service** — встроенный в Jakarta EE механизм планирования: контейнер
сам управляет таймерами, их потоками, транзакциями и (опционально)
персистентностью. Нужен, когда приложение и так работает на EE-сервере и хочется
планировать задачи «штатными» средствами платформы, без внешних библиотек.
Аналог Spring `@Scheduled`, но на стороне Jakarta EE.

## Два вида таймеров

- **Автоматический** — метод с **`@Schedule`**. Контейнер создаёт таймер сам при
  деплое. Поля (`second`, `minute`, `hour`, `dayOfWeek`, ...) задают расписание —
  это **свой** calendar-синтаксис EJB, похожий на cron, но не Unix-cron.

- **Программный** — таймер создаётся в коде через **`TimerService`**
  (`createSingleActionTimer`, `createIntervalTimer`, `createCalendarTimer`).
  Удобно, когда расписание известно только в рантайме.

## Ключевые понятия

- **`TimerService`** — фабрика таймеров; внедряется в бин через **`@Resource`**
  (это ресурс контейнера, не CDI-бин, поэтому не `@Inject`).

- **`@Timeout`** — метод-колбэк, который контейнер вызывает при срабатывании
  **программного** таймера; принимает объект `Timer`.

- **`Timer`** — дескриптор таймера: несёт `info` (произвольную нагрузку),
  следующее время срабатывания, позволяет отменить (`cancel`).

- **`@Singleton @Startup`** — бин создаётся в одном экземпляре при старте
  приложения; подходящее место для регистрации таймеров.

- **`persistent`** — у таймера есть флаг персистентности: персистентный таймер
  переживает рестарт сервера (хранится контейнером), `persistent=false` — живёт
  только в памяти.

## Полезно знать

- `@Schedule` calendar-синтаксис ≠ cron из тем `spring-scheduled`/`quartz`:
  другой порядок и имена полей, хотя идея «по календарю» та же.
- Без EE-контейнера бин — обычный POJO: аннотации не действуют, callback-методы
  можно вызвать вручную (что и делают тесты).
- Сравнение линейки: `scheduler` / `spring-scheduled` / `quartz` / `cron` —
  планировщики в SE/Spring; **EJB Timer** — то же, но средствами Jakarta EE.

## Запуск

```bash
./gradlew test    # проверка логики бина (без контейнера)
```

Для реального срабатывания таймеров бин нужно задеплоить на EE-сервер
(Payara/WildFly) — это вне рамок учебной ветки.
